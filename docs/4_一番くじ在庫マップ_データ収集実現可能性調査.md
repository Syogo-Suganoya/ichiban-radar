## 1. X API：料金体系の変更（最重要）

### 1-1. 何が変わったか

2026年2月6日、Xは固定ティア制を廃止し、新規開発者はすべて**従量課金（pay-per-use）**になりました。既存のBasic契約者も2026年6月1日以降、順次従量課金へ強制移行されています。**無料枠は読み取り用途には存在しません**（事前にクレジットを購入する前払い方式）。

### 1-2. 単価（公式ドキュメント記載値）

| 操作 | 単価 |
| :--- | :--- |
| **投稿（Post）の読み取り** | **$0.005 / 件** ＝ 約 **0.75円/件** |
| ユーザー情報の読み取り | $0.010 / 件 |
| いいね・ミュート・ブロック | $0.001 / 件 |
| 投稿の作成 | $0.015 / 件（URLを含む場合 $0.200） |

**月間上限：200万投稿読み取り／請求サイクル**（＝月$10,000）。これを超える場合はEnterprise（約$42,000/月〜）が必要。本サービスの想定規模では上限には当たりません。

> 補足：一部の国内ブログに「2026年4月改定でGET系が1/5に値下げ」との記述がありますが、公式ドキュメントの現行値は $0.005 のままです。**実際の単価はDeveloper Console上の表示が最終的な正**なので、クレジット購入前に必ず実画面で確認してください。

### 1-3. 課金を大きく左右する仕様：24時間デデュープ

**同一リソース（同一投稿ID）は24時間UTC以内なら何度取得しても課金1回**です。

これは本サービスにとって非常に有利です。「5〜15分ごとのポーリング」で同じ投稿が繰り返しヒットしても、課金は1日1回で済みます。ただし**UTC日付をまたぐと再課金される**ため、`since_id` による差分取得は必須実装です。

### 1-4. レート制限（コスト以外の制約）

| エンドポイント | Per App | Per User |
| :--- | :--- | :--- |
| `/2/tweets/search/recent` | 450 req / 15分 | 300 req / 15分 |
| `/2/tweets`（一括取得） | 3,500 req / 15分 | 5,000 req / 15分 |

recent searchは1リクエスト最大100件なので、**450 × 100 = 45,000投稿 / 15分**＝理論上1日約430万投稿。発売日ピークでも余裕があり、**レート制限は制約になりません**。なお、クレジットを多く積んでもレート制限は緩和されません。

### 1-5. クエリ長制限：512文字 ← 設計を規定する制約

| 検索種別 | クエリ長上限 |
| :--- | :--- |
| Recent Search（直近7日、セルフサーブ） | **512文字** |
| Full-Archive Search | 1,024文字 |
| Enterprise | 4,096文字 |

**企画書 4-① の「`店舗名` + `一番くじ`」というクエリ設計は成立しません。** 店舗名を数十〜数百件ORで並べると512文字を即座に超過します。

**採るべき設計：**

```
("一番くじ" OR "一番賞") (完売 OR 売り切れ OR 残り OR ラストワン OR 引いてき OR 入荷 OR 在庫)
lang:ja -is:retweet
```

店舗の特定は**取得後にGeminiが本文から抽出**し、ジオコーディングで座標に変換する——という後段処理に寄せます。これは元の技術仕様書の②AI推測エンジンの役割とも整合しています。

## 2. コスト試算（X API + Gemini）

### 2-1. 1投稿あたりの処理単価

| 内訳 | 単価 | 比率 |
| :--- | :--- | :--- |
| X API 投稿読み取り | 0.75 円 | **約96%** |
| Gemini 3.1 Flash-Lite 解析（入力200tok / 出力100tok想定） | 約 0.03 円 | 約4% |
| **合計** | **約 0.78 円 / 投稿** | |

Geminiの単価（$0.25 / 1M入力、$1.50 / 1M出力）で計算。**AI解析費はX APIの取得費の約1/25で、実質的に誤差**です。コスト管理の対象は「何件取得するか」の一点に絞られます。

### 2-2. フェーズ別の月次・年次コスト

| フェーズ | 想定取得量 | 月額 | 年額 |
| :--- | :--- | :--- | :--- |
| **Phase 1（PoC）**<br>1タイトル・都内限定・発売週3日 | 約 5,000 投稿（一過性） | — | **約 4,000 円**（総額） |
| **Phase 2（β版）**<br>全国・主要タイトルのみ・絞り込みクエリ | 約 50,000 投稿/月 | 約 **3.9万円** | 約 **47万円** |
| **Phase 3（本運用）**<br>全国・全タイトル・広めのクエリ | 約 200,000 投稿/月 | 約 **15.6万円** | 約 **187万円** |
| （参考）月間上限 | 2,000,000 投稿/月 | 約 150万円 | — |

※ 取得量は「大型発売日 月4回 × 2〜3万投稿 + 平常日 3,000投稿/日」を基準にした概算。**PoCで実測して確定させるべき最重要パラメータ**です。

### 2-3. 資金計画書（文書3）との差分

| 項目 | 原案 | 本調査の結論 |
| :--- | :--- | :--- |
| API通信・利用料 | 40〜100万円（「X APIのプラン依存」） | **β版までなら約47万円で原案レンジ内。Phase 3で187万円となり不足** |
| 初期の下限コスト | Basic $200/月 ＝ 年36万円が固定発生 | **固定費ゼロ。使った分だけ。PoCは4,000円** |

**リスクの性質が変わりました。** 「高い定額を払えるか」から「取得件数を制御し続けられるか」へ。予算オーバーは設定次第で青天井になり得るため、Developer Console の**支出上限（spending limit）設定は必須**です。

## 3. コスト最適化の打ち手（優先度順）

1. **`-is:retweet` を必ず付与** — RTは在庫情報としてほぼ無価値なのに1件0.75円で課金される。バズ投稿1本のRT数千件がそのまま費用になるため、効果が最も大きい
2. **`since_id` による厳密な差分取得** — UTC日跨ぎの再課金を防ぐ
3. **状態語のANDを必須にする** — 「一番くじ」単独では取得しない。「完売/残り/入荷/ラストワン」等を必ず伴わせ、母数を数分の1に圧縮
4. **時間帯別のポーリング頻度制御** — 発売日午前は5分間隔、平常日深夜は1時間間隔
5. **信頼アカウントのリスト監視を併用** — 「一番くじ報告」系アカウントのタイムラインは、ノイズが少なく単位コストあたりの情報価値が高い
6. **`lang:ja` の付与** — 海外の無関係投稿を除外

## 4. Instagram の実現可能性

結論：**「#一番くじ」「#ハイキュー一番くじ」のような個別ハッシュタグ指定の検索は、公式Graph APIで可能です。日本語タグにも対応しています。しかもAPI利用料は無料。**

一方で「自然文キーワードでの全文検索」（例：`完売`）はAPIに存在せず、**あくまでハッシュタグ起点**である点が設計上の分岐になります。

### 4-1. できること（`ig_hashtag_search` → `recent_media`）

```
GET /ig_hashtag_search?user_id={ig-user-id}&q=一番くじ   → ハッシュタグID を取得
GET /{ig-hashtag-id}/recent_media?fields=caption,media_url,permalink,timestamp,like_count
```

| 項目 | 内容 |
| :--- | :--- |
| 任意のハッシュタグ指定 | **可能**（日本語タグOK） |
| 取得できるフィールド | `id` / `caption` / `media_type` / `media_url` / `permalink` / `timestamp` / `like_count` / `comments_count` / `children` |
| **API利用料** | **無料**（Xの0.75円/投稿に対し0円。ここが最大の魅力） |
| レート制限 | 200 calls / 1時間 / ユーザー（Business Use Case制限）。1ページ最大50件なので理論上1万件/時 |

### 4-2. 制約（設計に直結する4点）

| 制約 | 内容 | 影響と対処 |
| :--- | :--- | :--- |
| **① 30ユニークタグ / 7日ローリング** | 1つのIGビジネスアカウントが7日間にクエリできるユニークタグは30個まで。**ただし同一タグの再クエリは枠を追加消費せず、7日タイマーもリセットしない** | 「常時監視する30タグ」を固定運用する分には支障なし。**制限されるのは"タグを入れ替える柔軟性"**。新作タイトルの追加を週次で計画する運用設計が必要 |
| **② 直近24時間の投稿のみ** | `recent_media` は実行時点から24時間以内に公開されたメディアしか返さない | 在庫マップの鮮度要件（企画書は12時間）とは整合。ただし**取りこぼすと二度と取れない**ため、継続ポーリングが必須。障害時のバックフィルが効かない |
| **③ App Review が必要** | `instagram_basic` に加え **Instagram Public Content Access** の審査承認が要る。承認用途は「ハッシュタグキャンペーンのコンテンツ発見」「ブランドに関する世論の把握」等と規定 | **最大の関門かつリードタイム要因**。本サービスの用途説明が審査を通るかは事前に読めない。着手は早いほどよい |
| **④ 応答が時系列順とは限らない** | ドキュメント上「chronological order を保証しない」。`after` カーソルのみでページング | `timestamp` で自前ソート＋既取得IDの重複排除が前提 |

その他の細かい制約：`username` は取得不可（投稿者の信頼度スコアリングができない）／プロモ投稿は除外／**他人のストーリーズは取得不可**。

### 4-3. データとしての質（Xとの違い）

| | X | Instagram |
| :--- | :--- | :--- |
| 探索の起点 | **自然文**（「完売してた」で直接引ける） | **ハッシュタグのみ** |
| 状態語の拾いやすさ | 高い | 低い（タグに「完売」は付きにくい） |
| 店舗名の所在 | 本文テキストに書かれやすい | **キャプションになく画像内にしかない**ケースが多い → Vision解析が必要 |
| 取得コスト | 0.75円/投稿 | **0円** |
| 2026年のタグ5個制限の影響 | — | 投稿者が付けるタグを厳選するため、`#一番くじ` `#作品名` は残りやすい一方、**店舗・地域系タグはほぼ消える** |

つまり **「Xは"状態"を拾うのが得意、Instagramは"どの作品がどこで動いているか"の面を無料で広く拾うのが得意」** という役割分担になります。Instagram側で店舗を特定するには、キャプション＋画像のVision解析（Gemini 3.1 Flash-Lite）が必要ですが、それでも1投稿あたり0.1円未満で、X経由より安く収まります。

### 4-4. 30タグ枠の運用設計案

| 用途 | 枠数 | 例 |
| :--- | :--- | :--- |
| 常設・基幹タグ | 3〜4 | `#一番くじ` `#一番くじ購入` `#ラストワン賞` `#一番くじ開封` |
| 主要タイトル別（月次ローテ） | 15〜20 | `#ハイキュー一番くじ` `#ドラゴンボール一番くじ` 等、発売カレンダーに連動 |
| 検証・実験枠 | 5〜10 | 精度検証中のタグ、新作の告知タグ |

### 4-5. 第三者スクレイピングAPIについて

Instagram/X 双方に非公式のスクレイピング系APIが多数存在しますが、**いずれも各社の利用規約違反**です（Xの利用規約は書面同意なきスクレイピングを明示的に禁止）。本件は**クラウドファンディングと補助金申請で事業内容を公開する前提**であり、規約違反のデータ取得手段を組み込むのは、資金調達の可否とサービス継続性の両面で許容できないリスクです。**採用しない方針を明記しておくことを推奨します**（補助金申請書では逆に「公式APIのみを使用」と書けることが加点材料になります）。

### 4-6. Instagram の推奨ポジション

**Phase 1（PoC）**：X単独で検証。Instagramは並行して**App Review申請だけ先に出しておく**（承認待ちの時間を先に消化する）。

**Phase 2（β版）**：承認が下り次第、Instagramを**無料の補助ソース**として併用。当面は「どの作品がどのエリアで動いているか」の面的トレンド把握と、Xで拾えなかった店舗の補完に用いる。

**併せて進める自前ソース**（Instagramの代替ではなく、どちらにせよ必要）：

1. **電話確認の外注**（資金計画書 3章）— 精度が必要な主要店舗はここでカバー
2. **監視範囲の最適化** — 費用は監視範囲（エリア×タイトル数）に比例するため、対象を絞れば確実に下がる
3. **Instagram公式アカウントの運用** — 収集とは別に**集客・拡散チャネル**として。くじ開封系インフルエンサーとの導線もこちら

> ⚠️ 当初は「自社UGC（ユーザー投稿）機能」でX API依存度を下げる案を置いていましたが、
> **一般ユーザー向け画面にログインを作らない方針**にしたため取り下げました（[6_収益計画書](6_一番くじ在庫マップ_収益計画書.md)）。

## 5. AI：Gemini 採用にあたっての注意点

- **モデル選定：`Gemini 3.1 Flash-Lite`**（$0.25 / 1M入力、$1.50 / 1M出力）。短文分類＋構造化出力という用途に最適で、コストは実質誤差
- **`Gemini 2.5 Flash-Lite`（$0.10 / $0.40）は 2026年10月16日に提供終了**。今から書くコードで採用してはいけません
- **Structured Output（JSONスキーマ指定）を使用** — 企画書の `【対象店舗】/【ステータス】/【確信度】` をそのままスキーマ定義に落とす
- **Batch API は入出力とも50%オフ**（最大24時間の遅延許容）。リアルタイム判定には使えませんが、**精度検証用の一括再解析・過去データのバックフィルには有効**。PoCの評価フェーズでコストを半減できます
- 技術仕様書（文書2）の `gpt-4o-mini` / `claude-3-haiku` の記述は、Gemini採用に伴い全面差し替えが必要です

## 6. ネクストアクション

1. **X Developer Console でアカウント開設し、実単価を実画面で確認**（公式ドキュメントとConsole表示の突合）
2. **支出上限（spending limit）を設定**してから最初のクレジットを購入
3. **クエリの実ヒット件数を実測** — $10〜20程度のクレジットで、大型発売日1日分の該当投稿数を計測する。これが全コスト試算の根拠になる
4. **Instagram：ビジネスアカウント＋Facebookページを用意し、Instagram Public Content Access の App Review を申請**（承認待ちが読めないため、Phase 1と並行して最速で着手する）
5. **Instagram：`#一番くじ` の1日あたり投稿数と、キャプションに店舗名が含まれる割合を実測** — 補助ソースとしての実効性はこの2数値で決まる
6. 実測値をもとに**資金計画書（文書3）のAPI費用欄を書き換え**
7. **技術仕様書（文書2）の改訂** — LLMをGeminiへ、Xのクエリ設計を「状態語AND＋AI側で店舗抽出」へ、Instagramをハッシュタグ起点の補助ソースとして追記
