## 1. 資金調達ストーリー（クラファン・補助金の狙い目）

「単なる在庫検索アプリ」ではなく、**「推し活支援×店舗の業務効率化×AI活用」**という社会的文脈で打ち出します。

### ① クラウドファンディング（CAMPFIRE、Makuake等）
* **ターゲット**: 一番くじファン、推し活層、コレクター
* **コンセプト**: 「【ハシゴの徒労をゼロに】SNS×AIで一番くじのリアルタイム在庫がわかるマップを作りたい！」
* **リターン案**:
  * **プレミアムプランの長期利用権**（お気に入り登録・在庫急変のプッシュ通知）
  * **優先監視リクエスト権**（「このお店」「このタイトル」を優先的に監視）
  * **スポンサー枠**（サイト上への名前掲載）

### ② 補助金（ものづくり補助金・小規模事業者持続化補助金・IT導入補助金など）
* **申請テーマ**: 「AI（LLM）とSNSテキスト解析を活用した、店舗問い合わせ対応DXおよび消費者利便性向上プラットフォームの開発」
* **採択のポイント**:
  * ユーザーの利便性だけでなく、**「店舗（コンビニ・書店等）への長時間の電話問合せを減らし、店舗業務のDXに貢献する」**という社会的課題解決の文脈を強調。
  * **データ取得は公式API（X API / Instagram Graph API）のみを使用し、規約違反のスクレイピングを一切行わない**方針を明記。コンプライアンス面の加点材料となる。

## 3. 「電話外注×AI」を組み合わせたハイブリッド運用設計

初期の情報密度と信頼性を担保するための**外注オペレーションとシステム連携フロー**です。

```
[ 大型タイトル発売日 ]
  ├── 1. AI（X）    : 自然文から在庫の「状態」を全自動で判定・プロット（カバレッジ重視）
  ├── 2. AI（IG）   : ハッシュタグ起点で「どの作品がどこで動いているか」を無料で補完
  └── 3. 認定員（外注）: 主要駅近くの店舗へ在庫確認架電 ➡ 専用管理画面から「確定在庫」を入力（精度重視）
```

### 3-1. 認定員制度（なぜ一般公募にしないか）

**在庫確認の架電は、クラウドワークスの[プロクラウドワーカー](https://crowdworks.jp/lp/procrowdworker)認定を受けたワーカー（本書では「認定員」と呼ぶ）のみに依頼します。** 単価は一般相場より割高になりますが、これは品質と追跡可能性を買うための費用です。

一般公募の単発ワーカーに開放した場合、次の2つのリスクが顕在化します。**いずれも事業を即死させ得るもの**です。

| リスク | 具体的な被害 |
| :--- | :--- |
| **イタズラ電話** | 店舗に直接の実害が及ぶ。**「店舗の電話問合せ負担を減らす」という本サービスの社会的意義と真っ向から矛盾**し、補助金申請の根拠自体が崩れる。1件でも表面化すれば店舗・権利者との関係は回復困難 |
| **虚偽・未確認の入力** | 「電話確認済み（確定情報）」バッジはサービスの信頼性の最後の砦。ここが汚染されると、AI推測の精度をいくら上げても無意味になる |

**単価を上げて母数を絞る**方が、事後の品質管理コストとレピュテーションリスクより安く付く、という判断です。

### 3-2. 認定はプラットフォームの制度を利用する

自前で認定制度を一から作る必要はありません。**クラウドワークスのプロクラウドワーカー認定を、そのまま選別基準として使います。**

**プロクラウドワーカーの認定基準（クラウドワークス側が3ヶ月ごとに審査）**

| 項目 | 基準 |
| :--- | :--- |
| 納品完了率 | 過去1年間で **90%以上** |
| 総合評価 | 過去累計で **4.8以上** |
| **コミュニケーション評価** | 過去累計で **4.8以上** |
| 獲得報酬額 | 過去1年間で月間200位以内に1回以上 |
| スカウト数 | 過去1年間で5回以上 |
| プロフィール・自己PR | 入力済み |

さらに上位の **TOPクラス**認定は「獲得報酬額が最上位」かつ「**本人確認**など規定項目登録済」が条件です。

**この制度を使う利点**

* **コミュニケーション評価4.8以上**という基準が、そのまま「店舗に対して失礼のない電話ができるか」の代理指標になる。架電業務との相性が非常に良い
* **納品完了率90%以上**が、途中放棄による欠測を防ぐ
* **本人確認・実績の担保をプラットフォーム側が継続的に審査してくれる**（自前の書類選考・本人確認が不要）
* 認定は3ヶ月ごとに再審査されるため、**品質が落ちたワーカーは自動的に対象から外れる**

**それでも自前で用意すべきもの**

認定が保証するのは「ワーカーとしての信頼性」であって、「本業務の遂行能力」ではありません。以下は自社で用意します。

1. **研修資料**：架電スクリプト、禁止事項、店舗への配慮事項
2. **確認テスト**：スクリプトと禁止事項の理解確認
3. **認定員IDの発行**：管理画面アカウントを個人単位で発行（入力ログを紐づけるため、アカウントの共有は禁止）

> つまり **「認定」はクラウドワークスに任せ、「教育」は自社で行う**という分担です。制度構築のコストを丸ごと省けます。

### 3-2b. 単価が割高になることの裏付け

プロクラウドワーカーは公表実績として**契約単価42%UP・月間契約額19%UP**とされています。つまり**割高な単価は本制度における自然な水準**であり、予算上の想定（1件100円＝一般相場の約2倍）は過大ではありません。

⚠️ **要確認**：「募集条件をプロクラウドワーカー限定に絞れるか」はクラウドワークスへの確認が必要です。絞り込めない場合は、**スカウト（指名）による直接依頼**、または応募者のプロクラウドワーカーマークによる選別で運用します。

### 3-3. 禁止事項（業務委託契約に明記する）

* サービス名を偽ること、**店舗関係者や購入客を装うこと**
* 同一店舗への短時間での複数回架電
* **混雑時間帯（11:30〜13:30、17:00〜19:00）の架電**
* 在庫確認以外の要求・質問
* **未確認情報の入力**（つながらなかった場合は「確認不可」として記録する）

### 3-4. 品質管理の仕組み

| 手段 | 内容 |
| :--- | :--- |
| **全件ログ** | 入力は認定員IDに紐づけて記録し、誰のどの入力かを常に追跡可能にする |
| **入力ペースの異常検知** | 1件あたりの所要時間が不自然に短い場合、架電せず入力している疑いとしてフラグ |
| **SNS推測との乖離検知** | AI推測と繰り返し乖離する認定員を自動抽出し、抜き打ち確認の対象とする |
| **クロス確認** | 別の認定員が同一店舗へ再架電し、入力の一致率を測定 |
| **店舗からの苦情窓口** | サイト上に設置。**苦情が1件でも発生した時点で該当認定員を即時停止**し、事実確認を行う |
| **認定取消基準の事前明文化** | 恣意的な運用を避けるため、取消条件を契約時に提示しておく |

### 3-5. 管理画面（認定員用UI）

**入力項目は「残り本数」と「A賞（上位賞）の有無」の2つだけにします。ステータス（完売/品薄/十分）は入力させず、残り本数から自動導出します。**

A賞の有無を聞くのは、**上位賞狙いのユーザーにとっては残数より重要な情報**だからです。架電スクリプトも「まだ残っていますか？　A賞は残っていますか？」の2問に固定します（それでも5秒で終わります）。

| 残り本数 | 自動判定されるステータス |
| :--- | :--- |
| **0** | 完売 |
| **1〜10** | 品薄 |
| **11以上** | 十分 |
| （確認不可） | 記録のみ。マップには反映しない |

**なぜステータスを入力させないか**

* **入力の手数が半分になる**。架電1件あたりの所要時間がそのまま単価に跳ね返るため、項目を減らすことが直接コスト削減になる
* **判断のブレをなくす**。「残り8本は品薄か十分か」の解釈を認定員に委ねると、人によって基準が変わりデータの一貫性が崩れる
* **閾値を後から一括で変更できる**。運用しながら「品薄」の基準を10本から5本に変えたい、といった調整が過去データを含めて即座に反映される
* 認定員は**電話で聞いた事実（数）をそのまま記録するだけ**でよく、解釈の責任を負わない

**その他の要件**

* スプレッドシート感覚で、店舗リストを上から順に埋めていける簡易フォーム
* 入力された情報は **「電話確認済み（確定情報）」バッジ**付きでマップ上に優先表示
* **「確認不可（不在・つながらず）」を明示的に記録できる選択肢**を必ず用意する（未確認を空欄で放置させないため）
* 架電スクリプトを画面上に常時表示：「一番くじ〇〇の在庫確認ですが、まだ残っていますか？」——5秒で終わる内容に固定する
* **一般ユーザー向け画面とは意図的にまったく異なるデザイン**にする（誤操作・取り違えの防止、および業務画面としての情報密度の確保）

### 3-6. 外注先の選定（要相談事項）

クラウドソーシング各社には**ディレクション代行・エージェント**が存在するため、認定員のプール構築と品質管理の一部を委託できないか相談します。

**相談時に確認すべき項目：**

0. **募集条件をプロクラウドワーカー限定に絞れるか**（絞れない場合はスカウトによる指名運用に切り替える。→ 3-2b）
1. **在庫確認架電の受注可否と実績**
   ⚠️ **「テレアポ」として発注しないこと。** 営業電話ではなく**店舗への短時間の在庫確認**であり、案件の性質・必要な人材層・単価相場がまったく異なります。伝え方を誤ると、想定と違う人材が集まります
2. **認定・研修プロセスを代行できるか**、その費用
3. **人材プールの規模と稼働可能時間帯**（発売日の**平日午前**に稼働できる人材が必要）
4. **品質保証の範囲**とトラブル時の責任分界点
5. **手数料体系と実質発注単価**
   システム利用料はワーカーの手取りを削るため（クラウドワークス 5〜20%、ランサーズ 一律16.5%）、**手取り100円を確保するには提示単価をその分上乗せする必要があります**。予算はこの実質単価で組むこと
6. **秘密保持契約と禁止事項（3-3）の遵守を担保する仕組み**

**候補**：クラウドワークス／ランサーズ（＋各社のディレクション代行）、コールセンター・BPO代行会社

## 4. ユニットエコノミクスの改善ストーリー

補助金・クラファン向けに提示する成長ストーリーです。**X APIが従量課金になったことで、この物語は「あった方が良い話」から「事業継続に必須の要件」に変わりました。**

| 段階 | 主なデータソース | 1件あたりのデータ取得原価 |
| :--- | :--- | :--- |
| 初期 | 認定員による電話確認 ＋ X API | 高い（1件100円＋0.75円/投稿） |
| 中期 | X API ＋ Instagram（無料） | 中（無料ソースの比率が上昇） |
| 長期 | Instagram主体 ＋ 監視範囲の最適化 | **低い（ユーザー数が増えても原価は増えない）** |

**ユーザーが増えても収集コストは増えない**（費用は監視範囲に比例し、閲覧者数には比例しない）——この構造を明示することが、事業計画としての説得力になります。

## 5. 今後のアクションプラン

1. **X Developer Console の開設と支出上限の設定**（クレジット購入前に必ず実施）
2. **実ヒット件数の実測** — $10〜20程度のクレジットで大型発売日1日分の該当投稿数を計測。**全コスト試算の根拠となる最優先タスク**
