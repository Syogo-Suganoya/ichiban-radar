## 1. データ収集層（Data Ingestion）

### 1-1. X（一次ソース）

* **API**: `X API v2` / `/2/tweets/search/recent`（Python）
* **課金モデル**: **従量課金（pay-per-use）**。投稿の読み取り **$0.005/件**（約0.75円）
  * 2026年2月にBasic/Proの定額プランは廃止済み。**無料枠なし・クレジット前払い制**
  * **Developer Console の支出上限（spending limit）設定を必須要件とする**

#### クエリ設計（512文字制限への対応）

Recent Search のクエリ長上限は **512文字**。**店舗名をORで列挙する方式は成立しない**ため、「状態語で広く取得し、店舗の特定はAI側で行う」設計を採る。

```
("一番くじ" OR "一番賞")
(完売 OR 売り切れ OR 売切 OR 残り OR ラストワン OR 引いてき OR 入荷 OR 在庫 OR 補充)
lang:ja -is:retweet
```

#### 取得ロジックの必須要件

| 要件 | 内容 | 理由 |
| :--- | :--- | :--- |
| **`-is:retweet` の付与** | RTを除外 | RTは在庫情報として無価値だが1件0.75円で課金される。**コスト削減効果が最大** |
| **`since_id` による差分取得** | 前回取得の最大IDを保持し差分のみ取得 | 同一投稿は24時間UTC以内なら課金1回だが、**日跨ぎで再課金される**ため |
| **時間帯別ポーリング間隔** | 発売日午前=5分 / 平常時日中=15分 / 深夜=60分 | 取得件数がそのまま原価になる |
| **`lang:ja` の付与** | 日本語投稿のみ | 無関係な海外投稿の除外 |
| **信頼アカウントのリスト監視** | 「一番くじ報告」系アカウントを別系統で監視 | ノイズが少なく単位コストあたりの情報価値が高い |

* **レート制限**（コスト以外の制約）: recent search 450 req/15分（App）、1リクエスト最大100件。**理論上430万投稿/日まで取得可能で、実質的な制約にならない**

### 1-2. Instagram（補助ソース・Phase 2以降）

* **API**: `Instagram Graph API` / `ig_hashtag_search` → `{ig-hashtag-id}/recent_media`
* **利用料**: **無料**
* **前提条件**: Instagramビジネス/クリエイターアカウント＋Facebookページ連携、`instagram_basic` 権限、**`Instagram Public Content Access` の App Review 承認**
  * **承認待ちのリードタイムが読めないため、Phase 1と並行して最速で申請する**

```
GET /ig_hashtag_search?user_id={ig-user-id}&q=一番くじ     → hashtag_id
GET /{ig-hashtag-id}/recent_media?fields=id,caption,media_url,permalink,timestamp,like_count
```

| 制約 | 実装上の対処 |
| :--- | :--- |
| 30ユニークタグ / 7日ローリング（同一タグの再クエリは枠を消費しない） | **監視タグを30枠のマスタとしてDB管理**し、週次で入れ替え計画を回す。基幹4枠＋タイトル別20枠＋実験枠6枠 |
| `recent_media` は**直近24時間の投稿のみ** | **取りこぼすと二度と取得できない**ため、最低でも4時間おきの定期実行と失敗時リトライを必須化。バックフィル不可 |
| 応答が時系列順とは限らない（`after` カーソルのみ） | `timestamp` で自前ソート＋取得済みメディアIDによる重複排除 |
| `username` 取得不可 | 投稿者ベースの信頼度スコアリングはX側のみで実施 |
| 他人のストーリーズは取得不可 | 仕様として割り切る |

* **日本語ハッシュタグに対応済み**（`#一番くじ` `#ハイキュー一番くじ` 等をそのまま指定可能）
* 2026年のInstagram本体のタグ5個制限により、**店舗・地域系タグはほぼ付かない**前提で設計する

### 1-3. 店舗マスター・位置情報（ジオコーディング）

* **Google Maps Geocoding API** または **国土地理院API**（住所 → 緯度・経度）
  * 店舗マスターは事前に一括構築し、**ランタイムでの都度ジオコーディングは行わない**（コスト・レイテンシ対策）
* **店舗スクレイピング**: `Playwright` / `BeautifulSoup4`（公式サイトの取扱店舗一覧の事前取得用）
* AIが抽出した店舗表記（「〇〇駅前のローソン」等）は、**店舗マスターへの曖昧一致（あいまい検索＋エリア絞り込み）**で名寄せする

## 2. AI・自然言語処理層（AI & NLP Engine）

* **プログラミング言語**: `Python 3.9`（**実行環境はDocker**。`docker compose run --rm scripts ...`）
  * ⚠️ Pydantic のモデル定義では `X | None` ではなく `Optional[X]` を使うこと。3.9 では実行時評価で `TypeError` になる
* **LLM API**: **Google Gemini API — `gemini-3.1-flash-lite`**
  * **単価**: $0.25 / 1M入力トークン、$1.50 / 1M出力トークン
  * **1投稿あたり約0.03円**。X APIの取得費（0.75円）の約1/25で、**コスト管理上は誤差**
  * ⚠️ 最安の `gemini-2.5-flash-lite` は **2026年10月16日に提供終了**のため採用しない
* **構造化出力**: Gemini の **Structured Output（JSONスキーマ指定）** を使用し、出力形式を保証する
* **画像解析（Instagram用）**: Instagramはキャプションに店舗名がなく画像内にのみ存在するケースが多いため、同モデルの**Vision入力**を併用する
* **Batch API**: 入出力とも**50%オフ**（最大24時間遅延）。リアルタイム判定には使えないが、**精度検証の一括再解析・過去データのバックフィルに使用**
* **非同期処理・ジョブキュー**: `Celery` + `Redis`（発売日当日の大量投稿を非同期キューイング）

### 出力スキーマ（例）

```json
{
  "is_relevant": true,
  "store_hint": "〇〇駅前 ローソン",
  "area_hint": "東京都渋谷区",
  "title": "人気タイトル",
  "status": "LOW_STOCK",
  "remaining_hint": 3,
  "top_prize": "AVAILABLE",
  "confidence": 0.82,
  "reason": "「ラストワン賞まであと3枚」という具体的な残数記述"
}
```

* `status` は `SOLD_OUT` / `LOW_STOCK` / `IN_STOCK` / `UNKNOWN` の4値
* **`top_prize` は `AVAILABLE` / `GONE` / `UNKNOWN` の3値。在庫数とは独立した軸として扱う**
  * 「くじは残っているが上位賞は無い」は頻出であり、上位賞狙いのユーザーには残数より重要な情報になる
  * マップ上では「A賞あり」での絞り込みに使用する
* `confidence` はマップ表示のフィルタ閾値およびクロス検証のスコアリングに使用
* 実装は `scripts/schema.py`（Pydantic）と `web/src/lib/types.ts` の2箇所にあり、**必ず同時に更新する**

### 店舗名の名寄せ（`scripts/pipeline.py`）

AIが抽出した店舗表記（「〇〇駅前のローソン」等）を店舗マスターに突き合わせる。

* 正規化（NFKC・記号除去）＋**チェーン名の略称展開**（ファミマ→ファミリーマート、セブン→セブンイレブン）
  * ⚠️ 長音「ー」は削らない。チェーン名の識別に不可欠で、削ると別チェーンと衝突する
* 2-gramの包含率と全体類似度の高い方を採用し、**閾値0.7未満は「特定できず」として捨てる**
  * 誤った店舗にプロットするのは、情報が無いことより有害なため

## 3. バックエンド・データベース層（Backend & DB）

* **APIサーバーは立てない**。HTTPを受けるのは Next.js の **Route Handler**（`web/src/app/api/`）だけ
  * ⚠️ 当初はFastAPIを別途置く構想だったが、**採用しない**。UIが必要とするのは「解析済みの結果」を返す少数のエンドポイントだけで、そのために別プロセス・別デプロイ・別認証を持つ割に合わない。セッションCookieを跨いで共有する手間も消える
  * Pythonが担うのは**バッチ処理のみ**（収集・Gemini解析・名寄せ・DB書き込み）。HTTPは受けない
* **データベース**: **Neon (PostgreSQL + PostGIS)**
  1. **PostGIS**: 「現在地から半径2km以内の店舗」といった空間クエリを高速実行
  2. **ゼロスケール**: 無通信時はコンピュートが停止し、アクセスで自動復帰する
  3. **ブランチ**: 本番のコピーを数秒で作れるため、ステージングDBに使う
  * ⚠️ リアルタイム通知（WebSocket）は**採用しない**。バッチは1日数回で、変化の通知は Web Push が担うため（[デプロイ手順書](9_デプロイ手順書.md)）
* **認証・ユーザー管理**: **一般ユーザーと管理画面で、セッションを完全に分ける**
  * Cookie名（`kuji_user_session` / `kuji_admin_session`）も署名の名前空間も別。1つのセッションに `role` を持たせる方式より、権限の取り違えが起きにくい
  * 一般ユーザーの**ログインは任意**。未ログインでも地図・店舗詳細・A賞フィルタは使え、ログインで増えるのはお気に入りと通知（プレミアムプラン）
  * 管理画面（在庫確認コンソール）は**ログイン必須**。新規登録には招待コード（`ADMIN_SIGNUP_CODE`）が要る
  * scrypt によるパスワードハッシュ＋HMAC署名Cookieで自前実装（`web/src/lib/auth.ts`）
  * ⚠️ **マネージドな認証基盤へは移さない。** 一般ユーザーと管理画面でCookieも署名の名前空間も分ける設計を維持するため（CONTRIBUTING 不変条件⑥c）
  * **オペレーターIDはリクエストボディではなくセッションから取得する**（入力ログの追跡可能性を守るため）
* **主要テーブル（想定）**

| テーブル | 役割 |
| :--- | :--- |
| `stores` | 店舗マスター（名称・住所・`geography(Point)`・チェーン種別） |
| `titles` | 一番くじタイトルマスター（発売日を含む） |
| `posts_raw` | SNS投稿の生データ（`source`: x / instagram、投稿ID、本文、取得日時） |
| `inventory_signals` | AI判定結果（店舗ID・タイトルID・status・confidence・根拠投稿ID） |
| `verified_reports` | 電話確認済みの確定在庫（オペレーター入力） |
| `operators` | 管理画面のアカウント（メール・パスワードハッシュ・表示名） |
| `ig_hashtag_slots` | Instagram 30枠の監視タグ管理（登録日・7日タイマー） |
| `api_usage` | X API消費クレジットの日次記録（予算監視用） |

## 4. フロントエンド・UI層（Frontend & Map UI）

* **フレームワーク**: `Next.js` (React / TypeScript)
  * SSR/SSG対応による初期表示の高速化とSEO対策（OGP画像生成など）
* **地図描画ライブラリ**: `MapLibre GL JS`
  * Google Maps JS APIの描画課金を回避し、**OpenStreetMap系のベクタータイル**を利用
* **スタイリング・UI**: `Tailwind CSS 4`（スマホ表示最優先のレスポンシブ対応）
  * ⚠️ UIライブラリは入れていない。コンポーネントは `web/src/components/` に自前で置く。**管理画面と一般画面を意図的にまったく別のデザインにしている**ため、共通のデザインシステムに乗せる利点が薄い（CONTRIBUTING 不変条件④）
* **アイコン**: `Font Awesome`（ブランドアイコンのみ。SVGをバンドルし、CDNは使わない）
* **表示上の要件**
  * SNS推測ピンには**「AI推測」バッジ**、電話確認済みには**「確定情報」バッジ**を付与し、信頼度を明示する
  * **推測であることの免責表示**を常時明記（誤情報による空振りのUX対策）
* **広告枠**: 画面下部に固定高さのプレースホルダを確保する。**後から広告が挿入されて地図が飛ぶ（CLS）のを防ぐ**ため（[8_広告・アフィリエイト実装ガイド](8_広告・アフィリエイト実装ガイド.md) 5-4）

## 5. インフラ・ホスティング（Infrastructure & DevOps）

**「常時起動が必要なWebアプリ」と「1日数回だけ動く重いバッチ」を、実行モデルごとに分けて配置する。** 同居させると、バッチのために常時起動ぶんの費用を払うことになる。

| 役割 | 採用技術 | 選定理由・特徴 |
| :--- | :--- | :--- |
| **Webアプリ（UI + API）** | **Cloud Run**（サービス） | Route Handler・httpOnly Cookie・scrypt・Web Push送信をサーバー側で行うため、静的ホスティングでは成立しない。リクエスト従量・ゼロスケール |
| **収集・解析バッチ** | **Cloud Run Jobs** | 実行して終了する処理。実行時間ぶんのみ課金される |
| **バッチの定期実行** | **Cloud Scheduler** | 月3ジョブまで無料。**実行間隔がそのままX APIの請求額になる**（6章） |
| **データベース** | **Neon** | PostGIS対応・ゼロスケール・ブランチ機能。ローカル検証は Docker の `postgis/postgis` |
| **シークレット** | **Secret Manager** | Cloud Runの環境変数は平文表示されるため、キー類はこちらに置く |
| **地図タイル（地図背景）** | **MapTiler** | ⚠️ 未設定時はOSM公式タイルにフォールバックするが、**規約上その状態での本番運用は不可** |

構築手順（CLI・画面操作の両方）は [9_デプロイ手順書](9_デプロイ手順書.md) にある。

## 6. コスト制御（本サービス特有の設計要件）

X APIが従量課金になったことで、**取得件数がそのまま原価**になった。コスト制御はアプリケーション要件として実装する。

1. **Developer Console の支出上限を設定**してから運用を開始する（青天井の防止）
2. `api_usage` テーブルに日次消費を記録し、**予算閾値の80%到達でアラート、100%で収集停止**するサーキットブレーカーを実装
3. 取得件数の内訳（クエリ別・時間帯別）を可視化し、費用対効果の低いクエリを継続的に削る
4. 無料のInstagramの比率を上げ、**有償なXへの依存度を下げていく**ことを中長期のコスト戦略とする

## 💡 PoC制作の最短ルート（1〜2週間）

1. **Pythonスクリプト**でX APIから投稿取得（`-is:retweet` と `since_id` は初回から実装）
2. `gemini-3.1-flash-lite` の Structured Output でステータス判定
3. 判定結果を **Neon** に保存
4. **Next.js + MapLibre GL JS** で地図上にピン（赤・橙・緑）をプロット

> PoC段階でのX API費用は**約4,000円**（1タイトル・都内限定・発売週3日想定）。定額プランの下限が消えたため、小さく始めるコストはほぼゼロ。
