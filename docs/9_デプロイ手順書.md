# デプロイ手順書（Google Cloud + Neon）

**構成の方針:** Webアプリは **Cloud Run**、データベースは **Neon**、バッチは **Cloud Run Jobs + Cloud Scheduler**。

このサービスは「常時起動が必要なWebアプリ」と「1日数回だけ動く重いバッチ」の2つに分かれます。両者を同じ場所に置くと、バッチのために常時起動ぶんの費用を払うことになるため、**実行モデルごとに置き場所を分けます**。

---

## 1. 全体構成

| 構成要素 | 置き場所 | 課金モデル |
| :--- | :--- | :--- |
| Webアプリ（Next.js） | **Cloud Run**（サービス） | リクエスト従量・ゼロスケール |
| PostgreSQL + PostGIS | **Neon** | ストレージ＋コンピュート従量 |
| 収集・解析バッチ（Python） | **Cloud Run Jobs** | 実行時間ぶんのみ |
| バッチの定期実行 | **Cloud Scheduler** | 月3ジョブまで無料 |
| コンテナイメージ | **Artifact Registry** | 保管容量 |
| APIキー・シークレット | **Secret Manager** | ほぼ無料 |
| Gemini | **Google AI Studio の APIキー** | トークン従量 |

```
[X API / Instagram Graph API]
            │  (Cloud Scheduler が起動)
            ▼
   [Cloud Run Jobs: Python バッチ] ──▶ [Gemini]
            │
            ▼
        [Neon (PostGIS)]
            ▲
            │  DataSource 経由でのみ読む
   [Cloud Run: Next.js] ──▶ 一般ユーザー / 管理画面
```

### なぜこの構成か

**Cloud Run を選ぶ理由は、Next.js のサーバー機能をそのまま動かせるからです。** 本サービスは Route Handler・httpOnly Cookie・scrypt によるパスワードハッシュ・Web Push の送信をサーバー側で行うため、静的ホスティング（Firebase Hosting 単体・GitHub Pages）では成立しません。

**Neon を選ぶ理由は、PostGIS が使える Postgres をゼロスケールで持てるからです。** 店舗検索は `ST_DWithin` に依存しており（技術仕様書 3章）、PostGIS は必須要件です。Cloud SQL でも動きますが、最小構成でも月数千円が常時かかるのに対し、Neon は無料枠から始められます。

> **代替案:** Firebase App Hosting も内部は Cloud Run です。GitHub 連携が最初から付く反面、ビルド設定の自由度は下がります。**Cloud Run を直接使うほうが、後述のバッチ（Cloud Run Jobs）と操作体系が揃うため運用が単純になります。**

## 2. 事前に必要なコード変更

⚠️ **現状のコードはそのままでは本番デプロイできません。** 先に次の3点を済ませてください。

### 2-1. `MockDataSource` は本番で使えない

モックの実体は `globalThis` 上のメモリです。Cloud Run はインスタンスが複数立ち上がり、かつ無通信で停止するため、**登録したユーザーが次のリクエストで消えます**。本番は必ず実DBに接続してください。

⚠️ **接続情報が無いと、エラーにならず黙ってモックで起動します。** 切り替えスイッチを廃止し「接続情報があれば実データ」という判定に一本化しているためです。検知手段は次の2つで、**デプロイ後に必ず両方を確認してください**。

- Cloud Run のログに `[data] ⚠️ 本番環境: データベースの接続情報が無いため…` が出ていないか
- 画面右上に「モックデータ」バッジが出ていないか

### 2-2. Neon 用の `DataSource` 実装

`web/src/lib/data/neon.ts` は未実装のスタブです。全メソッドを実装してください。

```bash
npm i @neondatabase/serverless
```

`data/index.ts` の判定は `DATABASE_URL` の有無で行うよう実装済みです。**インターフェース（`source.ts`）とUI側は一行も変えません**（CONTRIBUTING 不変条件⑤）。

DDLは `db/init/01_extensions.sql` の拡張有効化がそのまま使えます。Neon は PostGIS と pg_trgm に対応していますが、リージョンやプランで差が出ることがあるため、作成直後に実際に流して確認してください。

### 2-3. Next.js を standalone 出力にする

Cloud Run のイメージを小さくするため、`web/next.config.ts` に1行足します。

```ts
const nextConfig: NextConfig = {
  output: "standalone",
  turbopack: { root: path.join(__dirname) },
};
```

## 4. Neon（データベース）

Neon はコンソール操作が中心です。

**プロジェクトを作る**

1. [neon.tech](https://neon.tech) にサインイン（GitHubアカウントで入れます）
2. ダッシュボードの **「New Project」**
3. 入力する項目

| 項目 | 値 |
| :--- | :--- |
| Project name | `ichiban-radar` |
| Postgres version | **16** |
| Cloud provider | **AWS** |
| Region | **Asia Pacific 1 (Tokyo) — ap-northeast-1** |

4. **「Create project」**

**リージョンは必ず東京にしてください。** Cloud Run の `asia-northeast1` と物理的に近く、1リクエストで何度もSQLを投げるため往復遅延がそのまま体感速度になります。**作成後にリージョンは変更できません。**

**拡張を有効にする**

1. 左メニューの **「SQL Editor」**
2. 次を貼り付けて **「Run」**

```sql
CREATE EXTENSION IF NOT EXISTS postgis;
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

3. エラーが出ないことを確認する

**ここで失敗したら先に進まないでください。** PostGIS が使えないと店舗の近傍検索が成立せず、構成そのものを見直すことになります。

**接続文字列を控える**

1. 左メニューの **「Dashboard」** → **「Connect」**（または画面右上の **「Connect」**）
2. ダイアログで **「Connection pooling」のトグルをON**にする
3. 表示された文字列をコピーする

```
postgresql://user:pass@ep-xxxx-pooler.ap-northeast-1.aws.neon.tech/kuji?sslmode=require
```

⚠️ **ホスト名に `-pooler` が入っていることを目視で確認してください。** Cloud Run はリクエストごとにインスタンスが増減するため、プーリングなしの直結だとすぐに接続数上限に達します。**トグルをONにし忘れるのが、この手順でいちばん多いミスです。**

**ステージング用のブランチを作る（任意）**

1. 左メニューの **「Branches」** → **「New Branch」**
2. 名前 `staging` ／ 親ブランチ `main` → **「Create」**

本番データのコピーが数秒でできます。ステージング用の Cloud Run サービス（`kuji-staging`）からは、こちらのブランチの接続文字列を向けます。

## 5. シークレットの登録

**環境変数に直接書かず、Secret Manager に入れます。** Cloud Run の環境変数はコンソール上で平文表示され、デプロイコマンドの履歴にも残るためです。

```bash
printf '%s' "$(openssl rand -hex 32)" | gcloud secrets create AUTH_SECRET --data-file=-
printf '%s' 'postgresql://...-pooler.../kuji?sslmode=require' | gcloud secrets create DATABASE_URL --data-file=-
printf '%s' '<Gemini APIキー>' | gcloud secrets create GEMINI_API_KEY --data-file=-
printf '%s' '<X Bearer Token>' | gcloud secrets create X_BEARER_TOKEN --data-file=-
printf '%s' '<Instagram 長期トークン>' | gcloud secrets create IG_ACCESS_TOKEN --data-file=-
printf '%s' '<VAPID 秘密鍵>' | gcloud secrets create VAPID_PRIVATE_KEY --data-file=-
printf '%s' '<管理画面の招待コード>' | gcloud secrets create ADMIN_SIGNUP_CODE --data-file=-
```

実行用サービスアカウントに読み取り権限を与えます。

```bash
gcloud iam service-accounts create kuji-run

gcloud projects add-iam-policy-binding <PROJECT_ID> \
  --member="serviceAccount:kuji-run@<PROJECT_ID>.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"
```

### 画面操作

**シークレットを1つずつ登録する**

1. ≡ → **「セキュリティ」** → **「Secret Manager」**
2. **「シークレットを作成」**
3. 名前に `AUTH_SECRET`、**「シークレットの値」**欄に値を貼り付け
4. **「シークレットを作成」**
5. 上の表の7件ぶん繰り返す

`AUTH_SECRET` の値は、ターミナルで生成したものを貼り付けます。

```bash
openssl rand -hex 32
```

⚠️ **「シークレットの値」欄に貼るとき、末尾の改行が混入しないように注意してください。** 改行込みで保存されると署名が一致せず、**原因の分かりにくいログイン失敗**になります。

**サービスアカウントを作る**

1. ≡ → **「IAMと管理」** → **「サービス アカウント」**
2. **「サービス アカウントを作成」**
3. 名前 `kuji-run` → **「作成して続行」**
4. **「ロールを選択」** で **「Secret Manager のシークレット アクセサー」** を選ぶ
5. **「続行」** → **「完了」**

⚠️ この画面には **「鍵」タブがありますが、JSONキーは作らないでください。** 鍵ファイルは一度漏れると失効させるまで有効なままです。CI/CDからの認証は§8の Workload Identity 連携で行います。

## 6. Webアプリを Cloud Run へ

### 6-1. `web/Dockerfile`

```dockerfile
FROM node:22-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:22-slim AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
# NEXT_PUBLIC_* はビルド時にバンドルへ埋め込まれる。実行時の環境変数では差し替わらない
ARG NEXT_PUBLIC_MAPTILER_KEY
ARG NEXT_PUBLIC_VAPID_PUBLIC_KEY
RUN npm run build

FROM node:22-slim AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/public ./public
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
EXPOSE 8080
ENV PORT=8080
CMD ["node", "server.js"]
```

`web/.dockerignore` も置きます。

```
node_modules
.next
.env*
```

### 6-2. ビルドとデプロイ

```bash
gcloud builds submit ./web --tag asia-northeast1-docker.pkg.dev/<PROJECT_ID>/kuji/web:latest
```

```bash
gcloud run deploy kuji-web \
  --image asia-northeast1-docker.pkg.dev/<PROJECT_ID>/kuji/web:latest \
  --region asia-northeast1 \
  --service-account kuji-run@<PROJECT_ID>.iam.gserviceaccount.com \
  --allow-unauthenticated \
  --min-instances 0 --max-instances 5 \
  --memory 512Mi --cpu 1 --concurrency 80 \
  --set-env-vars VAPID_SUBJECT=mailto:you@example.com \
  --set-secrets AUTH_SECRET=AUTH_SECRET:latest,DATABASE_URL=DATABASE_URL:latest,ADMIN_SIGNUP_CODE=ADMIN_SIGNUP_CODE:latest,VAPID_PRIVATE_KEY=VAPID_PRIVATE_KEY:latest
```

`--max-instances` は**必ず設定してください**。指定しないと、バグや攻撃でリクエストが増えたときに青天井でスケールし、そのぶん Neon の接続数と課金も跳ねます。

### 6-3. 画面操作でデプロイする

イメージのビルドだけはターミナルで行い（`gcloud builds submit`）、そのあとコンソールで進めます。

1. ≡ → **「Cloud Run」** → **「サービスを作成」**
2. **「既存のコンテナ イメージから1つのリビジョンをデプロイする」** を選ぶ
3. **「選択」** → **「Artifact Registry」** タブ → `kuji/web` → `latest`
4. 次を設定する

| 欄 | 値 |
| :--- | :--- |
| サービス名 | `kuji-web` |
| リージョン | `asia-northeast1（東京）` |
| 認証 | **「未認証の呼び出しを許可」** |
| CPUの割り当て | **「リクエストの処理中にのみCPUを割り当てる」** |

5. **「コンテナ、ボリューム、ネットワーキング、セキュリティ」** を展開する

**コンテナ**タブ:

| 欄 | 値 |
| :--- | :--- |
| コンテナポート | `8080` |
| メモリ | `512 MiB` |
| CPU | `1` |
| 最小インスタンス数 | `0` |
| **最大インスタンス数** | **`5`** |

**変数とシークレット**タブ:

- **「変数を追加」** で `VAPID_SUBJECT` = `mailto:you@example.com`
- **「シークレットの参照を追加」** で `AUTH_SECRET` / `DATABASE_URL` / `ADMIN_SIGNUP_CODE` / `VAPID_PRIVATE_KEY` を、それぞれ**「バージョン」を `latest`**、**「参照方法」を「環境変数として公開」**で追加

**セキュリティ**タブ:

- **サービスアカウント**に `kuji-run` を選ぶ

6. **「作成」**

⚠️ **最大インスタンス数の既定値は100です。** ここを5に直し忘れると、暴走時に想定外の請求が発生します。**この画面でいちばん重要な入力欄です。**

デプロイが終わると、画面上部に `https://kuji-web-xxxx.a.run.app` というURLが出ます。開いて地図が表示されれば成功です。

### 6-4. 独自ドメイン

```bash
gcloud beta run domain-mappings create --service kuji-web --domain kuji-radar.example.com
```

画面から行う場合は、**Cloud Run のサービス一覧の上部にある「ドメインのマッピング」** → **「マッピングを追加」** → サービス `kuji-web` とドメインを指定します。ドメインの所有権確認（Search Console）を求められたら、画面の指示に従ってTXTレコードを登録します。

いずれの方法でも、表示されたレコードをDNSに登録すれば証明書は自動発行・自動更新されます。**反映まで最大で数時間かかります。**

## 7. バッチを Cloud Run Jobs へ

`scripts/Dockerfile` がそのまま使えます。**サービス（常時待受）ではなくジョブ（実行して終了）** としてデプロイする点だけが違います。

```bash
gcloud builds submit ./scripts --tag asia-northeast1-docker.pkg.dev/<PROJECT_ID>/kuji/batch:latest
```

```bash
gcloud run jobs create kuji-collect \
  --image asia-northeast1-docker.pkg.dev/<PROJECT_ID>/kuji/batch:latest \
  --region asia-northeast1 \
  --service-account kuji-run@<PROJECT_ID>.iam.gserviceaccount.com \
  --command python --args pipeline.py \
  --task-timeout 900 --max-retries 1 \
  --set-secrets GEMINI_API_KEY=GEMINI_API_KEY:latest,X_BEARER_TOKEN=X_BEARER_TOKEN:latest,IG_ACCESS_TOKEN=IG_ACCESS_TOKEN:latest,DATABASE_URL=DATABASE_URL:latest
```

手動で1回試します。

```bash
gcloud run jobs execute kuji-collect --region asia-northeast1 --wait
```

### 画面操作でジョブを作る

1. ≡ → **「Cloud Run」** → 上部の **「ジョブ」** タブ → **「ジョブを作成」**

⚠️ **「サービス」ではなく「ジョブ」タブです。** サービスとして作ると常時待受になり、走っていない時間も課金対象になります。

2. コンテナイメージに `kuji/batch:latest` を選ぶ
3. 設定する項目

| 欄 | 値 |
| :--- | :--- |
| ジョブ名 | `kuji-collect` |
| リージョン | `asia-northeast1` |
| タスク数 | `1` |
| タスクのタイムアウト | `900` 秒 |
| 再試行回数 | `1` |

4. **「コンテナ、変数とシークレット」** を展開
   - **コンテナ**タブ → **「コンテナ エントリポイント」** に `python`、**「引数」** に `pipeline.py`
   - **変数とシークレット**タブ → `GEMINI_API_KEY` / `X_BEARER_TOKEN` / `IG_ACCESS_TOKEN` / `DATABASE_URL` をシークレット参照で追加
   - **セキュリティ**タブ → サービスアカウント `kuji-run`
5. **「作成」**
6. 一覧でジョブを選び **「実行」** を押す
7. **「ログ」** タブでエラーが出ていないことを確認する

**再試行回数は1にしてください。** X APIは従量課金なので、失敗したジョブが何度も再実行されると、**そのぶん重複して課金されます。**

### 定期実行

```bash
gcloud scheduler jobs create http kuji-collect-schedule \
  --location asia-northeast1 \
  --schedule "0 8,12,18,21 * * *" --time-zone "Asia/Tokyo" \
  --uri "https://asia-northeast1-run.googleapis.com/apis/run.googleapis.com/v1/namespaces/<PROJECT_ID>/jobs/kuji-collect:run" \
  --http-method POST \
  --oauth-service-account-email kuji-run@<PROJECT_ID>.iam.gserviceaccount.com
```

⚠️ **実行間隔がそのままX APIの請求額です。** X API は1投稿の読み取りごとに $0.005 の従量課金です（調査書4章）。スケジュールを1日4回から1時間毎に変えると請求は約6倍になります。**間隔を変更するときは必ず調査書の試算を更新してください**（CONTRIBUTING「コストに直結する変更」）。

まずは1日4回（発売直後・昼・夕方・夜）から始め、実測を見て調整するのが安全です。

**画面から設定する場合は、ジョブの詳細画面にある「トリガー」タブ → 「スケジューラ トリガーを追加」** が最短です。スケジュール `0 8,12,18,21 * * *`、タイムゾーン `日本標準時（JST）`、サービスアカウント `kuji-run` を指定すれば、上のURLは自動で組み立てられます。

## 8. CI/CD（GitHub Actions）

**サービスアカウントキーのJSONは発行せず、Workload Identity 連携を使ってください。** 鍵ファイルはGitHubのSecretに置いた時点で漏洩リスクが恒久化しますが、連携方式なら短命トークンだけがやり取りされます。

```yaml
# .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write

jobs:
  web:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.WIF_PROVIDER }}
          service_account: deployer@<PROJECT_ID>.iam.gserviceaccount.com
      - uses: google-github-actions/setup-gcloud@v2
      - run: gcloud builds submit ./web --tag asia-northeast1-docker.pkg.dev/<PROJECT_ID>/kuji/web:${{ github.sha }}
      - run: |
          gcloud run deploy kuji-web \
            --image asia-northeast1-docker.pkg.dev/<PROJECT_ID>/kuji/web:${{ github.sha }} \
            --region asia-northeast1
```

タグに `github.sha` を使うのは、**問題が起きたときに前のリビジョンへ即座に戻せるようにするため**です。`latest` だけだと戻る先が特定できません。

```bash
gcloud run services update-traffic kuji-web --to-revisions <前のリビジョン名>=100
```

## 9. 本番環境変数の一覧

| 変数 | 置き場所 | 必須 | メモ |
| :--- | :--- | :---: | :--- |
| `DATABASE_URL` | Secret | ✅ | Neon の**pooled**接続文字列。**未設定だと黙ってモックデータで起動する** |
| `AUTH_SECRET` | Secret | ✅ | 未設定だとデプロイのたびに全員ログアウト |
| `ADMIN_SIGNUP_CODE` | Secret | ✅ | 未設定だと**誰でも管理画面に登録できる** |
| `NEXT_PUBLIC_MAPTILER_KEY` | ビルド引数 | ✅ | 未設定時のOSMタイルは規約上、本番利用不可 |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | ビルド引数 | – | 未設定なら通知機能のみ無効 |
| `VAPID_PRIVATE_KEY` | Secret | – | 同上 |
| `VAPID_SUBJECT` | 環境変数 | – | `mailto:` 形式 |
| `GEMINI_API_KEY` | Secret（Jobs） | ✅ | バッチ側のみ |
| `X_BEARER_TOKEN` | Secret（Jobs） | ✅ | バッチ側のみ |
| `IG_ACCESS_TOKEN` | Secret（Jobs） | – | Phase 2 |

**`NEXT_PUBLIC_*` はビルド時にバンドルへ焼き込まれます。** Cloud Run の環境変数に後から入れても反映されないため、`--build-arg`（またはCloud Buildの置換変数）として渡す必要があります。ここは踏みやすい落とし穴です。

## 10. つまずきやすい点

**ゼロスケールのコールドスタート。** `--min-instances 0` だと初回アクセスに数秒かかります。β版の間は許容し、正式公開時に `--min-instances 1` にします（常時起動ぶんは月1,000円前後）。

**Neon のオートサスペンド。** 無通信が続くとコンピュートが停止し、復帰に数百ミリ秒〜数秒かかります。Cloud Run のコールドスタートと重なると体感が悪化するため、公開前に両方の待ち時間を実測してください。

**セッションCookieは `Secure` が必要。** Cloud Run は常にHTTPSなので問題になりませんが、独自ドメインをHTTPで受けるプロキシを挟むと切れます。

**Web Push は HTTPS と Service Worker の登録パスに依存します。** `public/sw.js` がルート配信されていることを本番URLで確認してください。

**費用アラートを最初に設定してください。** X API と Gemini はどちらも従量課金で、バッチのバグ（無限ループ・重複取得）がそのまま請求になります。

1. ≡ → **「お支払い」** → **「予算とアラート」** → **「予算を作成」**
2. 名前 `kuji-monthly`、対象は作成したプロジェクト
3. 予算額に月の上限（例: `10000` 円）
4. しきい値を **50% / 90% / 100%** で設定し、メール通知をONにする

⚠️ **これは請求を止める機能ではなく、通知するだけです。** 上限に達しても課金は続きます。確実に止めたい場合は、`--max-instances` とジョブの実行間隔で入口を絞るしかありません。

### ログの見かた

障害時に最初に見る場所です。

- **Cloud Run**: サービス（またはジョブ）の詳細 → **「ログ」** タブ。アプリの `console.error` もここに出ます
- **Cloud Scheduler**: ≡ → 「Cloud Scheduler」 → 対象ジョブの **「ログを表示」**。定期実行が発火したかはここで確認します
- **Neon**: ダッシュボードの **「Monitoring」** で接続数とCPUを確認。接続数が張り付いていたら、pooled接続文字列を使えていない可能性が高いです
